# AIsa 全功能替换验收标准（讨论稿 v0.1）

日期：2026-10-17，北京时间。代码基线：`dd4ff77`。
状态：仅完成范围核对与标准起草；替换实现、候选服务实测和验收尚未执行。
本文阈值是建议的验收目标，不是现有程序已经达到的结果。开发前需冻结标准，不能测试失败后自行降低门槛。

## 1. 完成的定义

完整替换同时满足：

1. 生产部署不提供 AIsa 凭据、不调用 AIsa 或以 AIsa 为实际后端的代理服务。
2. 下述全部能力都有可工作的自动化替代实现，CLI、启动器与 MCP 均走替代路径。
3. 数据与分析质量达到各自标准，保留来源、地区、时间、精度和缺失信息。
4. 原有业务规则、历史状态及增量追踪没有非预期退化。
5. 实际费用达到冻结的预算目标；没有用漏采、少采或关闭功能制造节省。
6. 能提交可复现、可审计的测试证据，而不是只有成功截图或模拟测试。

无法承诺全球、永久、所有查询完全相同。可验收的是冻结范围内的功能完备和质量非劣。
模型文本不要求逐字一致；业务规则在相同输入上应一致；跨源数据差异应按约定口径衡量。
报告必须写明测试日期、地区、样本与观察周期，不能扩大为所有场景的绝对保证。

## 2. 必须逐项覆盖的能力

### A01 X 账号监听

代码：`radar/sources.py::x_new`。
替代接口应提供账号、帖子ID、发布时间、完整正文、原始链接、互动指标、分页状态。
测试覆盖空时间线、转推、回复、长文、同名账号、分页、高频发布和已删除帖子。
保留关注列表、30小时观察窗口、60天词汇基线及新词判断规则；切换不重置正式快照。

### A02 X 关键词搜索与用途证据

代码：`radar/usecases.py::evidence`。
保留关键词、时间、最低点赞、排除回复和排序语义；不能仅用账号时间线替代搜索。
需要验证分页、时间范围和正文，而不只是HTTP 200或返回数量。

### A03 名字判断

代码：`radar/judge.py::score`。
模型评分、阈值、跳过、错误降级都应保持有效；直接接入模型提供商。

### A04 用途提词与二次筛选

代码：`radar/usecases.py` 中模型提词和筛选调用。
保留用途证据、品牌标记、关联度筛选及原词与通用词区分。模型只分析实际提供的证据。

### A05 Google Ads 搜索量

代码：`radar/usecases.py::volumes`。
自动取得指定地区/语言的历史月量，保留月份、近似变体和供应商口径。
搜索建议数量、帖子数、Trends指数不能替代月搜索量。
CSV可用于人工核对和过渡，但仅CSV路径不满足完整自动化替换。

### A06 Google Trends 曲线、比较及规模估计

代码：`radar/usecases.py`、`radar/review.py::_series`。
保留单词曲线、与benchmark联合比较的曲线、地区、日期窗口、采样粒度与未稳定日期处理。
不能分别取两个独立0—100曲线后直接当作可比较大小；必须有一致的联合归一化或经过验证的校准方法。
保留现有通用词/名字规模估算及趋势判定的依据，不能只输出“上涨/下降”代替全部原字段。

### A07 Google 搜索首页

代码：`radar/competition.py::page_one`。
保留自然结果的URL、域名、标题、位置、页面类型，广告是否出现及SERP特性。
广告字段缺失必须是unknown，不能自动解释为没有广告；不能用其他搜索引擎结果充当Google结果。

### A08 关键词难度

代码：`radar/competition.py::difficulty`。
必须有真实数据或获准且独立验证过的替代方法；模型打分不等于原供应商KD。
广告竞争度不等于自然排名难度。跨供应商评分必须记录来源并重新校准阈值，不能直接复用20/40等门槛。
若声称数值本身等价，应使用相同上游指标和版本，而不仅是同样0—100的取值范围。

### A09 新域名及排名发现

代码：`radar/new_sites.py`。
需要发现候选域名，并同时取得注册日期、首次收录/首次被数据源发现时间、排名关键词数和预估自然流量。
仅查询已知域名WHOIS/RDAP，不能代替按条件发现新站，也不能把RDAP注册时间当作首次收录时间。
原AIsa接口已知错误不能作为“新实现同样失败即等价”的依据；用需求规则、上游样本和独立核验验收。

### A10 Reddit 求助和痛点数据

代码：`radar/social.py::reddit`、`radar/asks.py`、`radar/pains.py::reddit`。
保留查询语义、时间窗口、排序、正文、分数、评论数、subreddit、链接、时间戳、去重和排除规则。
仅使用网页搜索摘要不等于已经读取帖子正文。

### A11 YouTube 评论

代码：`radar/social.py::youtube_comments`、`radar/pains.py::tutorials`。
覆盖原有顶层评论读取和点赞字段，保留视频来源；关闭评论、视频不可用和配额耗尽应可区分。
只获取视频标题不能算替代评论能力。YouTube官方API可作为候选，权限与免费配额须实测。

### A12 需求分类、痛点聚类与教程线索

代码：`radar/asks.py::classify`、`radar/pains.py::group`、`tutorial_asks`。
请求/抱怨/解决方案/其他的业务语义，以及聚类证据索引、计数和建议词均应保留。
不能把同一条证据重复计数或生成不存在的引文。

### A13 14天复盘与报告决策

代码：`radar/review.py`、`radar/store.py`、`radar/report.py`。
保留到期判断、历史基线、多个搜索变体、hit/miss/no_data、days_ahead和按来源统计命中率。
相同输入时优先级、竞争降级、首次/复查时间、已知词过滤和排序规则应保持一致。

边界：GitHub/HF/Sitemap/GSC/邮件/TrustMRR及GoAnyAPI的原有独立能力不属于AIsa替换本身，但必须回归测试。
特别是GoAnyAPI的相关词、国家曲线、域名评级、广告供给与Chrome评价，不能在重构中无意丢失。

## 3. 证明零AIsa依赖

### 静态证据

- 生产入口的调用图不再依赖AIsa路由、chat或专用工具协议。
- 清点源码、默认配置、启动脚本、CLI、MCP、计划任务和兼容路径。
- 若保留旧代码用于离线基线，应明确隔离且不能被生产入口选择；文档中的历史字符串不算网络依赖。
- 配置中不要求AIsa Key；只有缺少新服务自身的必要凭据才报配置错误。

### 动态证据

- 在干净环境中移除AIsa凭据，禁止读取旧CLI登录文件和环境变量回退。
- 将`aisa.call`、`aisa.call_all`、`aisa.chat`设为抛错，执行全部入口；调用次数必须为0。
- 在网络层拒绝AIsa域名及未批准的外连地址，并记录全部生产请求，包括线程、异步任务、子进程和MCP路径。
- 允许名单中仅有选定的独立服务；供应商是否实际转发AIsa还需文档、合同或明确供应商说明，不能仅凭域名不同断言。
- 先用故意调用AIsa的负例确认拦截/记录器确实有效，避免“没有日志”其实是检测器失效。

通过标准：无AIsa配置仍能完成全覆盖测试；AIsa调用0、AIsa外连0、隐式回退0。
仅做源码关键词搜索、只跑daily或只mock掉网络，均不足以证明这一点。

## 4. 三层效果验证

### 第一层：确定性规则与数据契约

保存经过脱敏的旧接口原始响应，转换到统一数据结构；新适配器也转换到相同结构。
用同一份统一输入分别驱动旧业务规则与新系统，冻结时间、时区和配置。

必须100%通过：必需字段、稳定ID、日期/单位转换、分页终止、去重、新词规则、状态读写、关键词过滤、趋势计算、复盘及决策。
旧规则有明确缺陷时单独登记并修改规格，不以复制缺陷为验收目标。
原有113项测试必须保持通过；新增适配器、配额和故障测试也必须通过。模拟测试不替代真实服务验证。

### 第二层：真实数据的对齐比较

同一账号/关键词、同一语言地区和时间窗；成对查询尽量相隔不超过5分钟。保存精确请求时间和查询参数。
数据源之间不要求严格逐字相同，差异必须解释；同一查询翻页后的并集参与比较，不能只比较返回数量。

建议首轮样本：全部35个关注账号、至少30个X搜索查询、50个SEO关键词、20个新站查询/核验案例、20个Reddit查询和20个视频。
SEO词需覆盖新词、成熟词、低量词、歧义词和确实无数据的词；不得只挑返回良好的样本。
数字是验收样本下限，不代表一次上线就自动执行这些付费查询；须先确定测试费用上限。

建议阈值：

- X：明确时间窗内、经核实有效的参考帖子ID召回率≥95%；有效帖子精确率≥98%；重点发布清单100%捕获；必需字段完整率≥99%。
- 参考集合由AIsa结果、新接口结果及独立核查共同形成，人工处理差异；AIsa不是完整真值，不计算“全站召回率”。
- X新鲜度：衡量同一轮采集时的新增覆盖和最新帖可见时间；成对测试的p95额外延迟建议≤5分钟。
- Google首页：URL规范化后Top10集合重合率中位数≥70%，不足10条按实际可见集合计；明显差异需重复核验地区、设备和采集时间，不能强造排名。
- 搜索量：采用同上游、同地区、同月份、同变体口径时应精确一致；跨源时至少90%的可比词相对误差≤20%，并报告原始数值、缺失率与变体归并。
- 零量/低量词不使用除以零的相对误差；范围量不能当精确值比较。旧侧有数据而新侧缺失的词计入覆盖失败，不能从分母删掉。
- Trends：对齐同地区、时间窗、粒度后，有效变化曲线相关系数≥0.90、峰值日期偏差≤一个采样周期、业务趋势判定一致率≥90%。
- 平坦/低量/全零曲线不计算无意义相关性，按no_data或稳定样本单独评估；不同归一化方案需先校准，不能直接比较指数。
- KD：同指标同版本应一致；换指标时需至少50个带人工参考的词做阈值校准，open/mixed/crowded决策一致率≥90%，关键错判逐条复核。
- 新站：必须同时满足原规则的两个日期和关键词/流量条件；抽查记录真实性100%，参考候选覆盖率≥90%；缺少候选发现能力直接失败。
- Reddit/YouTube：原始ID、链接、正文、排序口径必须可追溯；同窗参考有效项召回率≥90%，缺失源记录为失败而非空结果。

上述跨源阈值是建议值，需在开发前确认；达不到就判失败或范围受限，不事后删除困难样本。

### 第三层：模型效果

至少200条人工标注的名字/普通词及歧义样本；至少100组用途、需求和评论证据样本。
样本分为调试集和保留验收集；保留集不用于反复调prompt。标注人先看证据，不看模型/供应商名字；争议样本另行裁决。

- 名字识别：精确率≥90%、召回率≥95%，且相较同集AIsa基线的任一指标下降不超过3个百分点。
- 用途/需求：人工判定有证据且相关的结果占比≥90%，对标注核心用途覆盖率≥90%。
- 需求分类：四类macro-F1≥0.85，不能通过把多数项归为other提高表面准确率。
- 痛点聚类：证据ID必须存在、计数与去重一致、没有引文捏造；可操作性/相关性按冻结评分表由人工评分。
- 证据引用真实性100%，模型伪造搜索量或KD等外部数值0例；原始数据自身的真伪需另行核实。
- 合法结构化输出成功率≥99%；坏输出应报错/受控降级，不得伪造已完成分析。
- 每组模型验收输入至少重复3次，报告均值与最差值；不能只展示最好的一次。

DeepSeek分数不与旧模型逐个精确对齐，重点验证阈值后的判断与最终研究质量。

## 5. 端到端、稳定性与状态

- CLI：daily、sources、keywords、pains、leads；系统Bash启动器的setup/check；MCP的recent_leads、keyword_table、run_radar均覆盖。
- 周任务和到期任务必须强制触发或冻结时钟，不以“今天没到期所以没调用”通过。
- 14天复盘先使用固定历史样本与时间推进测试，再补真实到期样本；未补实测前注明“真实14天复盘待验收”。
- 连续7天、每天早晚两轮进行真实观察，至少14轮；其中至少一轮强制覆盖全部可选能力。
- 对35账号监听，按来源请求/账号记录成功率；建议有效采集成功率≥98%，任一账号连续两轮缺失必须报警并复核。
- 同输入同状态重复运行不重复入库；中断后重跑不丢游标、不漏帖；不得直接复用不同供应商的分页cursor。
- 生产state从备份副本做兼容测试；正式切换保留历史首次发现、复盘到期和累计命中记录。
- 带正确完整来源数据的样本才能声明本轮完整；401、402、429、504、JSON错误、缺字段、部分分页与额度不足必须可区分。
- 缺失值保留null及原因，不变成0、flat、无广告、低竞争或无需求；受控降级不等于完整验收通过。

## 6. 费用与免费额度

同一任务范围、样本、地区、频率和质量门槛下比较；不能仅按每千条宣传价估算。
记录每次请求、重试、页数、返回条数、唯一有效条数、模型输入/输出token、缓存命中、已知费用和未知费用。
核对供应商后台余额/用量变化，报告客户端记录与账单差异；请求失败不能自动记成免费。

不预设50%降本门槛或上限。先取得同工作量的旧方案账单与新方案实测，再冻结月预算和目标降幅；功能/质量门槛不得为了降本降低。
降幅按`1 - 新方案常规总成本 / 旧方案同工作量总成本`计算，分别列出模块成本、固定订阅费、模型费和数据费。
旧成本为零时不计算百分比；未知费用单列。预算目标未冻结时成本门标记BLOCKED，不能自行判定达标。
试用赠送额度与常规价格分别报告；不依靠一次赠送或未计算订阅费宣称长期便宜。
每日/每月累计限额跨进程重启有效；额度用尽停止该项，不自动充值或切换收费备用源。
若需严格硬金额上限，供应商也必须支持消费上限/报价或费用可预判；单靠本地计数不能控制上游未知扣费。

“完整功能”“稳定自动运行”“全部免费”不能提前同时保证；KD、新站排名数据等可能需要直接采购。
找不到合格免费替代时保留阻塞项，不通过关闭功能、人工CSV或模型猜数宣称全部替换完成。

## 7. 证据包与判定

每次验收保存到独立、默认不公开的evidence目录，包含：

- baseline.json：旧/新commit、配置哈希、模型版本、依赖、时间/地区、样本清单及所有阈值。
- capability-coverage.json：A01—A13各项的适配器、测试ID、数据来源、执行时间、结果和证据路径。
- sanitized-request-log.jsonl：端点、参数摘要、耗时、状态码、计费和重试；不得包含密钥、会话token或敏感原文。
- raw-samples/：条款允许保存的脱敏原始样本；不允许保存原文时保存获准的ID/哈希及复现步骤，说明证据限制。
- offline-results/、live-results/、model-evaluation/：机器可读指标、逐例差异和人工判定，不只存汇总图。
- network-audit/：外连允许名单、拦截负例、完整入口的实际外连记录。
- cost-reconciliation/：已脱敏的供应商用量与客户端记账核对。
- soak-runs/：14轮记录及故障恢复、历史状态兼容性证据。
- acceptance.md：每项结论、未解决问题、适用范围和最终裁决。

单项状态只能是PASS、FAIL、BLOCKED、NOT_RUN。NOT_RUN不是PASS；BLOCKED不是“暂时跳过但整体通过”。
部分替换可独立交付，但总称“完整替换通过”要求A01—A13全部PASS，以及零AIsa依赖、状态兼容和预算门槛全部通过。
严重错误、隐式AIsa回退、伪造市场指标、历史数据丢失任一出现，整体FAIL，不用平均分抵消。

## 8. 建议实施顺序与当前缺口

1. 冻结本标准、真实供应商清单、测试样本及独立测试费用上限。
2. 建统一数据契约和记账/外连审计，再用旧快照建立离线基线。
3. 接入DeepSeek、X、SEO、新站、Reddit、YouTube各适配器；每项先契约测试再小样本实测。
4. 用独立state影子运行，完成质量对比和七天观察，再做正式切换与回滚演练。
